### 一、老板要解决的两件事（已用生产库只读数据验证）

**背景**：尾端派送 = 一张 WD 代表一辆车一趟派送；建单接口 `POST /admin/lastmile/orders`（`apps/api/src/modules/admin-ops/routes.ts:540` 起）；候选运单来自前端 `fetchLastmileShipments`（`apps/web/src/services/business-api.ts:1012`）调 `GET /staff/shipments?all=1&status=inWarehouseTH,deliveryBooked,outForDelivery,delivered`（`apps/api/src/modules/shipments/routes.ts:437`）；工作台是 `apps/web/src/modules/lastmile/LastmileDispatchWorkspace.tsx`（管理员/员工共用）。

**分柜模型**（`apps/api/src/modules/shipments/parent-status.ts` 头注释）：装柜时从父单拆出子单，父单件数相应扣减；849 张分柜父单里 846 张自己 0 件、货全在子单上，父单状态只是汇总（跟最慢的子单走）；少数父单自己还留着货时状态是它自己那批货的。子单不能再装柜。

**事实 1：候选列表被 0 件父单淹没。** 生产库只读统计（2026-09-10）：可派送状态里「分过柜且自己 0 件」的父单 **1045 张**，全部出现在候选列表里；派送单一共 1062 行、671 张 WD，员工实际派的几乎全是子单（`-1`/`-2`/`-3`）；历史上误派过 0 件父单的行 11 条、父子都被派过的家族 1 个。另外 **8 张**父单有子单但自己还留着货（这些要保留）。

**事实 2：「不能重复派」挡住了正常的再派。** 建单接口 `:688-696`：一票货在别的 WD 里还是 DELIVERING（没签收）就 409。生产日志 2026-09-08 上午：员工要把前一天（WD000642，9-7 16:23 建）没签收的 4 票连同新货一起再派，建单被拒 **5 次**，最后把那 4 票在旧单里点了「签收」才建成 WD000647——「签收」会把运单写成 delivered，货如果没送到就是假状态。现在生产有 67 行派送中：54 行 3 天内、3 行 3–14 天、10 行 14–60 天；同一票货 2 条以上派送中行 = 0。

### 二、要做的改动（方案已和老板定；细节你可以改得更稳，但要在报告里说明理由）

#### 改动 A：候选列表不显示「分过柜且自己 0 件」的父单

1. 后端 `GET /staff/shipments`：当 `all=1` 时，给每条 item 加 `hasChildren: boolean`。实现：items 算完后，取本页里 `parentTrackingNo == null` 的 trackingNo 列表，一次 `prisma.shipment.findMany({ where: { companyId, parentTrackingNo: { in: [...] } }, select: { parentTrackingNo: true } })` 得到集合，回填。**只在 `all=1` 时查**（普通列表不多这一次查询）。不改 where、不改 take、不改现有字段（CLAUDE.md #8c：这个接口还有别的调用方，先 grep）。
2. 前端 `fetchLastmileShipments`：过滤掉 `hasChildren && (packageCount ?? 0) === 0` 的父单；父单自己还留着货的（packageCount > 0）保留；子单一律保留。`LastmileShipmentItem` 加可选 `hasChildren`。
3. 后端建单接口兜底：循环里拿到 `ownShipment` 后（select 要多带 `packageCount`），如果它是父单（`parentTrackingNo == null`）且 `packageCount === 0` 且存在子单（`tx.shipment.findFirst({ where: { parentTrackingNo: ownShipment.trackingNo, companyId }, select: { id: true } })`，只读不锁），抛 `LastmileConflictError("运单 X 已分柜、货都在子单上，请勾选它的子单")` → 409。

#### 改动 B：「改派」——建单/追加时可以把还在别的 WD 里派送中的货挪过来

1. 建单接口 body 加可选 `moveFromDelivering?: boolean`（`:549` 那个类型）。
2. **不带**这个标志时行为不变（仍 409），但 409 的文案改成**列出全部**冲突的运单和各自的 WD（现在只报第一票）。要做到这一点，冲突检查得在循环前先批量查一遍：`tx.adminLastmileOrder.findMany({ where: { shipmentId: { in: shipmentIds }, companyId, status: "DELIVERING" }, select: { id, shipmentId, deliveryNo } })`。循环里原来那道 `busy` 检查保留（它是锁后的复查，防并发）。
3. **带**标志时，在同一个事务里：
   - 锁序必须是 **[2901 号码锁（只有新建时才拿）→ 旧派送单行 FOR UPDATE（按 id 排序）→ 运单（`lockShipmentsChildrenFirst`，子单先）→ 父单]**。签收/删除两条路是 [派送单 → 运单 → 父单]（`:762` 和 `:887` 那两处注释），全库只有建单拿 2901 且它在最前，所以这个顺序跟谁都不成环。**先锁旧派送单行，再锁运单**——反过来就会和签收/删除死锁。
   - 锁完旧行后**重读**它们的 status（CLAUDE.md #28）：仍是 DELIVERING 的才算「要挪的」；已经变成 SIGNED 的**不删**（签收完再派一趟本来就允许，见 `:670` 附近注释），照常给它建新行。
   - 对要挪的那票：`delete` 旧行（旧行是 DELIVERING，没有签收图）；新行照常创建；运单状态照常写 `outForDelivery`；**轨迹只写一条**，备注改成 `改派：从 WD旧 转到 WD新，` + 原来的出车文案（`:638` 的 `departRemark`），不要写两条。
   - 目标 WD 就是它现在所在的 WD（追加到同一张）→ 不算冲突，跳过这一票并在返回里告诉前端（`skipped: [...]`），别掉进 P2002 那个 409。
   - 返回 `{ deliveryNo, count, moved: number, skipped: string[] }`。
   - 旧 WD 挪空了不用处理（WD 只是按 deliveryNo 分组，空了自然不显示）。
4. 前端工作台：
   - 用 `props.lmOrderList` 算 `shipmentId → 派送中的 WD 号`（status === "DELIVERING"）。
   - 候选列表每一项：若在别的 WD 派送中，显示一个小标签「在 WD000xxx 派送中」（`:412-418` 那个 label 里，紧凑，不加颜色块）。
   - `submitDispatch`（`:140` 起）：提交前先本地预检，有冲突就 `confirm()`（项目里删除也用 confirm）：「下面 N 票还在别的派送单里派送中：\nYW0001489-1（WD000642）\n…\n确定要挪到这张单吗？旧单里会去掉，客户轨迹记一条「改派」。」确认后带 `moveFromDelivering: true` 提交；取消就不发。服务端 409 兜底：收到 409 且文案含「派送中」时同样弹这个确认再重试一次（并发场景）。
   - 成功提示带上挪了几票、跳过几票。
5. **不改**：签收接口、删除接口、状态流程、`LASTMILE_STATUSES`、数据库结构、任何存量数据。不写迁移。
