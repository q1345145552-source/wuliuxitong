「物流系统出处」那一栏里另外核出来的：

- 2.3 `volumeCbm`：**员工建单带了产品行时，整票方数是按产品行算出来的**（填的整票方数会被覆盖；测试里填 1.234、出来 1.152）。所以新单的「各款方数之和 ≈ 整票方数」；超管事后改整票方数就不一定了。约定说「只看占比」，不影响。
- 2.4 `products`：**员工建单没填产品明细时，系统也会自动补一行产品**（品名、箱数、货型都有，**长宽高是空的**）。所以「`products: []` 的老单」只剩 2026-07 以前的老数据；新单更常见的是「有一行、`volumeCbm: null`」。约定 2.4 说「有一款方数是 null → 这票待处理」—— **照这个规矩，员工没录尺寸的单全会进待处理**，见第六节要问的第 1 条。
- 2.5 `loadedAt`：装柜明细的 `created_at`，**是装柜操作那一刻**，不是柜子的装柜日期。
- 2.6 整柜的轨迹：整柜建柜时会写轨迹（已装柜那一步用装柜日期），所以 `statusHistory` 一般不是 `[]`（样例 3.6 写的 `[]`）。
- 3.10 样例：预报单没有轨迹时 `statusChangedAt` 我们给 `null`（样例写了个时间，跟 `statusHistory: []` 对不上；按 2.3「没有轨迹的老单给 null」的规矩给）。

## 二、加了哪些接口（都在 `/integrations/finance2/v1` 下，GET，只读）

| 接口 | 说明 |
| --- | --- |
| `GET /waybills/changes?since=&cursor=&limit=` | 约定 2.2。`since` 必须带时区；按 `changedAt`、再按运单号（字节序）排；`limit` 默认 200、最大 500；游标不透明。删掉的给删除记录。 |
| `GET /waybills/{运单号}` | 约定 2.8。传子运单号返回母运单那一票；删掉的给删除记录；从来没有过的 404。 |
| `GET /waybills/numbers?createdFrom=&createdTo=&cursor=&limit=` | 按订单建单时间列**现存**的母运单号 + `changedAt`（`deletedAt` 恒为 null，删掉的不在里面）。`createdTo` 可以不传。 |
| `GET /customers?cursor=&limit=` | 本公司 `role = client` 的全部账号，按唛头排、分页。 |
| `GET /agents` | 本公司全部代理。 |
| `GET /customers/agent-changes?since=&cursor=&limit=` | **约定以外多给的**：客户换代理的记录（从哪个代理换到哪个、什么时候），见第五节第 4 条。 |

- 响应外壳照约定 2.8：`{serverTime, items, nextCursor, hasMore}` / `{serverTime, item}`，不包物流系统自己的 `{code, data}`；出错 `{error, message}`（`bad_request` 400、`unauthorized` 401、`not_found` 404、`disabled` 503）。
- `serverTime` 是**数据库时钟**（改动记录也用数据库时钟，两边对得上）。
- 每个接口在**数据库只读事务**（`READ ONLY` + `REPEATABLE READ`）里查：写一个字数据库都会拒绝（测试 R2）；一页里的数据出自同一个快照。
- 只看 `FINANCE2_COMPANY_ID` 那一家（库里还有测试用的假公司）。
- **没做 429 限流**（约定 1.3 写了 429）。财务 15 分钟拉一次，暂时用不上；要加再说。
- 原来给海外仓财务系统的 `/integrations/finance/v1/…` 一个字没动。

真跑出来的样例返回（测试数据）：`docs/finance2-接口样例.json`。

## 三、加了哪些表、迁移，「改过也能看到」怎么做的

迁移 `apps/api/prisma/migrations/20261119_finance2_readonly_api/migration.sql`（只加不删，可以重复执行）：

1. `finance2_waybill_changes`（只追加）：母运单号、改动时间（数据库时钟 UTC、毫秒）、是不是删除、哪张表触发的。
2. `finance2_customer_agent_changes`（只追加）：唛头、原代理、新代理、时间。
3. **触发器**（15 个，7 个函数），挂在 `orders`、`shipments`、`order_products`、`shipment_container_items`、`status_logs`、`containers`、`users` 上：约定里用到的列一变，就往上面两张表插一笔。
4. 给现有的每一票母运单补一条（时间取订单 / 运单 `updated_at` 里晚的那个；已经有记录的不补）。

**为什么用触发器、没在业务代码里一处处加**（提示词铁律 4 说的是「在各处顺手记一笔」）：会改这几张表的地方有几十处（建单、改单、确认收货、到货通知、装柜卸柜、分柜并柜、柜子推进和撤销、尾端派送、拆派仓回传、删 / 恢复轨迹、整柜建改删、删订单、超管改号改唛头……），手写一定会漏，以后加功能的人也不会记得。触发器挂在表上，**哪条路改的都记得到，原有业务代码一行没改**。所以「在原有代码里加了哪几笔」的答案是：**一笔都没有**，原有代码只动了 `server.ts`（路由和登录解析，上面说了）和 `main.ts`（注册路由）。

触发器为什么不影响原流程：

- 一律 `AFTER … FOR EACH STATEMENT`，用变化行集合一次插完：批量推一个柜子也只多一条 INSERT。
- 只读别的表、只往两张新表插，**不更新、不锁别的行**，跟原来的加锁顺序无关，不会带出死锁。
- 整段包在 `EXCEPTION WHEN OTHERS` 里：记失败只发一句 WARNING，原操作照常成功（测试 R3：故意让改动记录表插不进去，改运单状态照样成功）。
- 只认约定里用到的列：付款状态、备注、国内单号、柜子状态、只碰 `updated_at` 这些都**不**算改过（测试 I9）。

哪些变化会让一票出现在 `changes` 里（都有测试）：建单、改单（体积重量件数货型仓库运输方式唛头审核状态整柜金额）、确认收货、产品行增删改、装柜 / 卸柜、拆 / 并子运单、状态（单张、柜子整柜推进、尾端派送、拆派仓回传，都是改 `shipments.current_status` + 写轨迹）、删 / 恢复 / 改轨迹、改柜号柜型装柜日期整柜标记、删订单、删整柜、改运单号。

**有一样不会**：客户换代理不会让他名下的运单出现在 `changes` 里（运单上的 `agentId` 是现在的代理，下一次这票有别的改动时才会带出新代理）。要看换代理请用 `/customers` 或 `/customers/agent-changes`。

## 五、跟约定对不上 / 我加的东西（财务那边要知道）

1. **唛头能改**（第 8 节第 15 条不对）：超管能改一票的唛头。改了会出现在 `changes` 里、`customerMark` 变成新的。约定第 4 节已经写了「确认后 `customerMark` 变了进待处理」，照那个办就行。
2. **运单号能改**：超管能改母运单号（拆过子运单的不许改）。改了以后**旧号**在 `changes` 里出一条**删除记录**，**新号**作为一票新运单出现（产品、轨迹、确认收货时间都跟过去）。财务那边会看到「一票被删 + 一票新的、确认收货时间一样」。要不要认成同一票，财务定（物流这边没有「旧号 → 新号」的对照，要的话可以再加）。
3. **整柜也有件数、装柜明细也有方数件数**（第 10 条），样例 3.6 的那几个 `null` 实际是数。
4. **多给了一个接口** `/customers/agent-changes`：从这次上线起，客户换代理的日子由物流系统记（精确到毫秒）。这能回答约定接口⑥：财务拿「确认收货时间」去这张记录里查，就知道确认收货那一刻属于哪个代理，不用按「财务拉到的那一刻」算。上线以前的换代理没有记录。用不用、怎么用财务定；不用也没关系，`/customers` 整份拉照旧可以。
5. `statusChangedAt` 是母运单**最新一条轨迹**的时间。员工删过轨迹、0 件母运单（状态跟子单推、不写轨迹）时它可能不是「进入当前状态的时间」。
6. `signedAt`：母运单已签收，并且子运单都签收了（**退回 / 取消的子单不等**，跟物流系统推父单状态一个口径），取这一家最后一条 `delivered` 轨迹。都签收了却一条签收轨迹都没有（老数据 / 删过轨迹）给 null。
7. `/waybills/numbers` 只列现存的母运单号，`deletedAt` 恒为 null（删掉的订单连建单时间都没了，没法按建单时间列）。删掉的财务从 `changes` 的删除记录拿。
8. 子运单只认跟母运单同一张订单的（跟原来那条财务接口一样）；挂错订单的脏子单不带出来。
9. 没做 429（见第二节）。
10. **`changedAt` 是「改的那一刻」，不是「提交的那一刻」（独立审查实测）**：同一票两个事务各改一处，先开始的晚提交时，财务可能先拿到「新体积 + 旧状态、changedAt = 后一个的时间」，下一轮这票会再出来（往回多拉 10 分钟能拉到），但 **changedAt 跟上次一样**。约定第 4 节写的是「changedAt 不比已存的新就跳过」—— 照这个会把这次的状态丢掉。**请财务改成「比已存的旧才跳过，相等照样更新」**。物流这边要根治得开数据库的 `track_commit_timestamp`（要重启数据库），这次没做。
11. 404 只在「取一票没有」时是 `{error:"not_found"}`；路径写错（比如 `/waybills/a/b`）、服务器出错这两种走物流系统原来的统一出错格式 `{code:…}`，财务别把路径错的 404 当成「没有这一票」。
12. 触发器的已知代价（独立审查实测）：每条真记了改动的语句多一个子事务，一个事务里超过 64 条时数据库会变慢一点（柜子推进时逐个同步父单可能碰上）；单条语句改 2000 行从 61 毫秒到 145 毫秒。现在事务都短，影响不大。**以后有迁移改了触发器用到的列（比如 `volume_m3` 改名改类型），要同时改触发器**，否则触发器每次都失败、被兜住，改动记录静默停掉、业务照常（WARNING 只进数据库日志）。上线后的核对见第七节第 5 步。

## 六、要问老板 / 财务的（攒在这里，没一条条问）

1. **员工建单没录尺寸的单会不会全进待处理？** 现在员工建单不填产品明细也会自动补一行（没有长宽高），这一行的 `volumeCbm` 是 null。约定 2.4 说「有一款方数是 null 就待处理」—— 照这个，这类单全进待处理。建议财务改成：**只有一款、或者全部款都没尺寸时，当「没产品明细」按整票货型算**；多款里有的有尺寸、有的没有才待处理。（物流这边原样给，不替财务猜。）

   `SELECT count(*) FROM shipments c WHERE c.parent_tracking_no IS NOT NULL AND NOT EXISTS (SELECT 1 FROM shipments m WHERE m.tracking_no = c.parent_tracking_no);`

   有的话先跟老板定怎么处理（修数据，或者这类单另说）。
