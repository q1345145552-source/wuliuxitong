# 2026-11-09 拆派仓签收时少送 / 补送 / 确认丢失写进运单轨迹

老板原话在拆派仓已定清单第 54～56 条（11-09）：三种情况都写进湘泰运单轨迹、客户看得到、运单状态不变；先上湘泰、再上拆派仓。

## 做了什么（只改后端，没改库、没加环境变量）
- `chaipai/events.ts`：DELIVERED 认可选的 `delivery`（SIGNED / SUPPLEMENT_SIGNED / LOSS_CONFIRMED + 件数）；格式不对当没带、不拒收；非 DELIVERED 带了不认。摘要只在认得了 delivery 时多算一格 —— 没带的摘要跟以前一字不差（老消息重发照样 DUPLICATE）。
  三句轨迹：`尾程派送已签收（WD…），实送 4 件，少 2 件`（送齐 / 没带照旧）、`补送 2 件已签收，累计送到 6 件`（没齐加「，还少 N 件」）、`少的 2 件确认丢失，累计送到 4 件`。
- `chaipai/event-routes.ts`：
  - 补送 / 丢失：只锁运单，不拿 WD 号锁、不锁也不动派送单、不去拆派仓取照片；去重 / 判旧照旧；记一条 `sl_cp_` 轨迹（员工不能单删），**前后状态一律写已签收**（签收以后的补充，标签跟句子对得上；不照收到时湘泰的状态写，否则签收在重试、补送先到时客户会看到「派送中」排在「已签收」后面）；运单状态不改；回 APPLIED。
  - **有意跟任务书不一样**：任务书写「照常更新回传进度（sequence / eventId）」，这里**不推进**。原因：拆派仓发件箱每条各自重试、不排队（`outbox.sender.ts` flushBatch），补送可能赶在还在重试的签收前头到；推进了序号，签收重发会被当旧消息扔掉、湘泰永远停在派送中；两条补送前一条晚到也会被扔掉。补送不改状态，只靠 eventId 去重。两轮 Codex / dsh 都同意。`chaipai_shipment_states.lastSequence` 现在的意思是「最后一条推进粗状态的回传」，不是所有回传的最大序号。
  - 第一次签收少送：员工先手工签过同一张派送单时（以前不重复写签收那句），带件数的那句照写（新信息）。
- `shipments/overview-counts.ts`：「本月已签收」只数从别的状态签进已签收的那条（`fromStatus ≠ delivered`），补送 / 丢失跨月不多算。生产 11-09 只读查过：已签收 → 已签收的老记录只有 3 条（7～8 月），不影响以前的数。
- `chaipai/photo-routes.ts`：状态表没这票时再看消息账本有没有 APPLIED 的回传（只收过补送的票员工也看得到派送照片）。

## 没动的（审查提到，按任务书或不在范围）
- 件数内部一致性不校验、格式不对的补送退回普通签收、丢失句不加「还少」：都照任务书。
- 原来就有的：员工给已签收的票再建一张派送单又删掉，`admin-ops` 那条修复轨迹（`sl_lmdel_`，派送中 → 已签收、时间是删单那天）会让「本月已签收」把上个月签收的算进本月。不是这次带出来的，没动（dsh 第 2 轮）。
