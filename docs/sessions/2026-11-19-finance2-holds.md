## 我自己定的技术取舍（汇报时说清）
- 「重新核对」**先只问唛头**：财务说不扣了 → 整个唛头放（到下一份更晚生成的名单为止）；还扣 → 再带母运单号问一次，说可以 → 只放这一票（连子单）。约定写的是「带唛头和母运单号问、回 false 就把唛头标成可放」，但带了运单号的 false 可能只是这一票单放，照约定会把整家都放了，所以分两次问。放和扣都记，按财务的核对时间取最新。
- 配错不等于关：开关开着就照本地名单拦（Codex 第二次审查第 1 条）。
- 核对放过的记录：新名单的 generatedAt 晚于核对时间才作废（比核对还早生成的名单没把这次核对算进去）。
- 时间一律写泰国时间（「按 2026-12-05 10:15（泰国时间）的名单」），跟财务系统2 一致。
- 被拦的提示只写唛头和运单号，不写客户名字、不写金额（名单里本来也没金额）。
- 日志不跟事务走（写坏了会连累原操作），拦的那一刻另起写。
- 加了 observe（试运行）档：上线先开 observe 看几天日志「本来会拦谁」，对了再开 enforce。
- 取名单失败的重试按约定 1.3（5 秒、30 秒、2 分钟）；「立即更新名单」按钮只试一次，定时任务正在取时直接回「正在取」。
- 「核对放过」记的是财务回的 checkedAt（没有就用它的 serverTime），不用物流服务器的钟：要跟财务名单的 generatedAt 比先后。
- 拿到的名单比本地的还旧（财务名单时间往回跳）不替换、记成失败（页面能看到「最近没取到」），打 error 日志。
- 报警：约定说 401/403、连续 1 小时取不到要报警。物流系统没有「异常提醒」页，先打 error 日志（线上日志能 grep 到「扣货名单取不到了」）。
- 开关 off：四个入口都先看开关再查库，跟改之前一条查询都不多；放货页那一块不显示、取到 off 就不再轮询。
- 「重新核对」「立即更新名单」不触发全公司页面实时重拉（加进 realtime/topics.ts 的 SKIP_EXACT）。
